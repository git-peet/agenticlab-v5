# AgenticLab V5.2 — Product Roadmap and Design Synthesis

**Status:** Working product direction and evidence synthesis; not an implementation authorization

**Prepared:** 2026-10-06

**Scope:** Re-anchor V5 in the intended AgenticLab product, synthesize the existing V4/V5 evidence, and recommend a first small vertical slice.

> “V5.2” names this design iteration in the project, not a release commitment. The ideas below have different evidence and maturity. A candidate is not a selected feature, and a recommendation is not approval to implement it.

## 1. Executive direction

AgenticLab is a **delivery-focused engineering system supported by persistent, project-specific knowledge across sessions**. It is not merely a memory tool, a prompt collection, or a fixed team of personas. V5 should preserve the outcomes that made V4 valuable while rebuilding the architecture around a coherent system, current agent runtimes, and a lower complexity and context-cost budget.

V5 must support two first-class ways of working:

1. **Default/free work:** the user begins with the default agent. It may answer directly, clarify, investigate, use a capability, recommend an established workflow, or coordinate bounded specialist work when justified.
2. **Explicit workflows:** the user deliberately invokes a known procedure when structured sequencing, handoffs, gates, or validation are useful—for example, substantial planning or implementation.

These are two entry paths through shared knowledge, context, governance, and verification contracts—not two separate systems. Workflows remain available; they are not mandatory ceremony for every task. Specialization remains useful, but the V4 fixed roster and invocation topology are not inherited automatically.

Memory and context engineering are central and intertwined, but they are not the whole product. V4 provides evidence that knowledge was captured and curated; how reliably and usefully retrieval affected work remains uncertain. V5 should make the knowledge loop testable in real use without requiring that question to block the whole system design.

**Working sequence:** define the product boundary; preserve research and audit candidates in a traceable portfolio; build a small, coherent V5 skeleton in the clean V5 repository; exercise one end-to-end path in a separate real-project playground; use targeted evidence to decide what to add next.

## 2. Product purpose and intended behavior

AgenticLab should help a human engineer deliver complex software work more accurately, efficiently, safely, and consistently than a strong coding agent used without AgenticLab-specific continuity and operating discipline. It should accumulate useful project knowledge, retrieve and verify it when relevant, support both conversational and structured work, preserve human authority, and adapt to available AI runtimes without making transient runtime features the system's identity.

A representative work loop is:

```text
human objective
  → understand scope and current state
  → assemble sufficient task context (including relevant verified history)
  → answer, investigate, plan, or choose an approved workflow
  → act within explicit authorization
  → verify the result and preserve recoverable state
  → propose useful learning for review
```

The system should explain material uncertainty and context choices proportionately. It should not load all memory by default, make every task a multi-agent workflow, turn model confidence into authority, or silently promote unverified experience into durable knowledge.

## 3. Product map: concerns that must fit together

These are architectural concerns, not a demand to implement one subsystem for every row.

| Concern | Product responsibility | Carry-forward posture |
|---|---|---|
| Operating model | Default/free mode and explicit workflows coexist and share contracts | Default is a normal entry point; workflows remain available for work that benefits from them |
| Project understanding | Use current code, project instructions, structure, domain knowledge, and prior work | Preserve useful topology/flow understanding; make generated maps and external analyzers optional unless earned |
| Knowledge lifecycle | Capture evidence, classify and scope it, review/promote it, retrieve, verify, correct, supersede, or discard | Memory is a major V5 capability; recording and consultation are separate questions |
| Context engineering | Select only context relevant to the next decision; enforce scope/freshness; make retrieval outcomes inspectable | Integrate with memory without making retrieval unconditional |
| Workflows and procedures | Offer repeatable delivery paths, skills, and potentially process routines | Preserve valuable procedure outcomes, not V4's entire prompt topology |
| Specialization | Use a lens, procedure, workflow, or isolated specialist where it improves the work | Isolation is important for independent review; a fixed persona roster is not required |
| Governance and control | Keep scope, approval, reversibility, deterministic safety, and stop conditions clear | Preserve strong control; rebuild exact mechanisms for V5 and its host |
| Continuity and learning | Recover interrupted work and record meaningful decisions/outcomes without logging every turn | Distinguish checkpoints, logs, evaluations, and durable knowledge |
| Runtime and adapters | Translate the same system contract into host capabilities | Harness-independent meaning; thin adapters with explicit capability gaps and fallback |
| Observability | Understand outcome quality, retrieval behavior, cost, latency, user attention, and failures | Measure targeted questions; do not build an instrumentation project as a prerequisite |

## 4. Synthesis method and evidence boundaries

The synthesis used the following sequence rather than treating every document or metric as equally authoritative:

1. **Purpose and actual operating model:** read V4's `MANUAL.md` and the first V5 roadmap to understand what AgenticLab claims to be and how default work, workflows, specialists, memory, governance, and adapters fit.
2. **V4 implementation evidence:** use the V4-to-V5 Neo audit and relevant improvement records to separate observed value from exact V4 implementation, historical workaround, and unresolved candidate. The audit reports coverage across V4 brain files, personas, system/utility/delivery prompts and workspace artifacts; this synthesis did not re-read old delivery workspaces.
3. **V5 design proposals:** compare the pipeline candidates and V5 brain/evaluation contracts. Treat pipeline and backlog entries as design inputs, not approved runtime behavior. The old pipeline index's Stage 6 execution status belongs to the first attempt and is not current V5.2 status.
4. **Experiment results:** use the recorded plans, controls, results, limitations, and decisions. Distinguish a model/tool activation result from task benefit, a synthetic fixture from real delivery, and a single-run directional signal from a stable effect.
5. **Disposition:** retain a concept when it protects demonstrated value or addresses a plausible product need; label its evidence and cost; merge overlapping ideas; park mechanisms with no demonstrated need; preserve the source lineage and why a choice was made.

### Evidence grades used here

- **Observed/documented V4 evidence:** a reported real artifact, incident, or metric in the V4 manual/audit/backlog. It supports a V4 claim, not automatically a V5 design.
- **V5 experiment:** a bounded result under its recorded fixture and controls. It supports only the tested comparison and stated limitations.
- **Prior-art concept:** a transferable idea from Hindsight, Jev, adapter research, or other reviewed sources. It is not proof of benefit in AgenticLab.
- **Design inference/recommendation:** a proposed product or architecture consequence; it still needs the user's decision and, where relevant, a later real-use check.

No claim below depends on unreviewed raw transcripts. Historical session mining remains out of scope under the current data boundary.

## 5. Findings from V4

The V4 manual shows an ambitious, integrated system: five memory types; several tiers and navigation structures; episodic-to-semantic consolidation; workflows and maintenance prompts; specialist roles; authorization and safety rules; Pi/Copilot adapters; and extensive self-observation. That history contains useful design knowledge, but it also demonstrates how layers accumulate and interlock.

The V4 audit and second-attempt diagnosis identify durable **functions** to preserve:

- Evidence-led exploration, design, implementation, and verification; some deliverables included repeated re-audits and correction of earlier wrong claims.
- Approval boundaries, explicit blockers, stop conditions, and deterministic safety where the host supports it.
- Checkpoints and recovery for multi-step work; independent review when shared context would compromise judgment.
- Deliberate memory correction, provenance, uncertainty, and review rather than assuming stored knowledge stays true.
- Self-measurement of recurring mechanisms and their cost.
- Default/free work as a real, increasingly common mode alongside explicit orchestration.

The same sources warn against carrying forward whole implementation families uncritically: fixed persona-owned memory, mandatory multi-persona choreography, unconditional Digest/MOC loading, V4 thresholds and path topology, one adapter accumulating many responsibilities, and maintenance commands that may impose recurring human/context cost.

The diagnosis reports one 17-session V4 sample with **zero cold-tier matches**, while another write-back reminder counter reached **1,235 fires** before a reset bug was corrected. It also reports $38.31 over six sessions and 84.7M cache-read tokens versus 421K output in that sample. These figures are evidence that activation, runaway prompting, and aggregate cost deserve attention; they do not prove that every memory or workflow mechanism failed.

## 7. Design implications

1. **Treat AgenticLab as the integrated product described above.** Do not reduce V5 to the memory benchmark or to a simplified prompt pack.
2. **Keep both modes explicit.** The default agent and a user-invoked workflow should share scope, knowledge, context, and safety semantics. Routing into an existing workflow must remain distinguishable from the user explicitly invoking it.
3. **Build the knowledge path as a small, inspectable loop.** Candidate experience is not durable truth; records need useful provenance and scope, human action for promotion, current-state checks where relevant, and visible distinction between no match, filtered records, and retrieval failure.
4. **Keep memory as evidence, not authority.** It cannot redefine task scope or authorize actions; active lifecycle state is not proof that the claim remains true.
5. **Use Hindsight concepts, not its infrastructure or automatic retention.** Evidence-backed observations, distinct retain/recall/reflect responsibilities, memory defense, and source-linked projections are candidates. External server/database, automatic retention, and unconditional injection are not selected.
6. **Use Jev as a possible bounded advisory decision method, not a universal pre-reasoning classifier.** Typed questions, explicit uncertainty/abstention, deterministic composition, and per-decision evaluation are useful patterns. Do not let confidence grant authority; actual API use is not selected. The memory-review/persistence prompt is a deferred candidate in C09: revisit it after real proposals reveal review friction, and never let advice replace human confirmation.
7. **Preserve researched pipeline candidates visibly.** Simplicity is not a reason to erase candidates. Each candidate instead needs a layer, source, evidence grade, cost/risk, status, dependency, and revisit trigger.
8. **Exploit current runtime features without making V5's core depend on one host.** Core contracts should be host-neutral; Pi-specific enforcement or lifecycle support needs a capability matrix and tests, not claims of parity based on matching prose.
9. **Measurement follows decisions.** Use lightweight task-level observations and targeted comparisons when they resolve an actual decision. Do not require a broad corpus, universal telemetry system, or arbitrary numeric gates before a first useful skeleton exists.

- product direction and constraints;

- historical V4 implementation details that are evidence, not V5 features.

Statuses describe maturity, not priority or approval: **framed**, **candidate**, **parked**, **selected** (requires explicit decision), **in progress**, **implemented**, **rejected**, **historical/reference**. No backlog status silently authorizes implementation.
