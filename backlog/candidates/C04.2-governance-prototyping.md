# C04.2 — Governance prototyping direction

**Status:** `candidate`; guidance document for the next C04 prototyping phase. This record is analysis and decision framing only. It does not select an implementation slice, authorize mutating changes, or permit a V4 governance port.

**Parent:** [C04 governance/safety](C04-governance-safety.md) · [C04 governance gap](C04-governance-gap.md) · [C04.1 cross-check and next step](C04.1-governance-cross-check-and-next-step.md) · [C03 context engineering](C03-context-engineering.md)

**Recorded:** 2026-11-22

## Purpose

Capture the audit result and durable guidance for C04 prototyping after the C02/C03 checkpoint.

The aim is **not** to reproduce V4 governance in V5. The aim is to understand which V4 governance concepts remain valuable, express them in V5-native terms, and avoid adding mechanisms that conflict with V5's default-first, low-friction, selective-context direction.

## Working principles for the coming phase

1. **Always prefer the elegant option.**
   - Reuse existing contracts, prompts, adapters, and tests before adding new artifacts.
   - Prefer one reusable semantic rule over several overlapping rules.
   - Prefer native harness/tool capabilities before bespoke machinery.

2. **Do not add friction.**
   - Do not add confirmations for work already explicitly authorized and bounded.
   - Do not add ceremony to default work.
   - No new prompt, gate, tool, candidate, or maintenance loop without a concrete observed problem it solves.

3. **Discuss tradeoffs explicitly through those two lenses.**
   - Semantic rules are cheap but enforcement is weak.
   - Deterministic guards are stronger but can overblock and become host-specific.
   - Extra confirmations reduce risk but interrupt flow.
   - New artifacts improve clarity but create maintenance cost.

4. **Audit before implementation.**
   - Reconcile documentation with the current generic payload and current delivery paths.
   - Treat V4 as evidence and prior art, not as a specification.
   - Select a slice only after a concrete gap and failure mode are named.

## Executive conclusion

C03 was useful, but it was the wrong vehicle for governance.

C03 addresses **what context the agent selects and assembles**. C04 addresses **what the agent is authorized to do, how scope and safety boundaries are expressed, and what stops unauthorized or unsafe action**.

Recent C02/C03 work improved retrieval, context assembly, handoff, validation, and workflow friction. It also produced governance-adjacent evidence: approval handoffs, protected knowledge reads, inactive candidate staging, separate promotion, and model-dependent tool-use reliability. Those are inputs to C04, not a replacement for C04.

V5 already has a smaller but meaningful governance baseline. The next work should be a **bounded C04 current-state/action-boundary review**, not a V4 migration and not immediate implementation of every gap in `C04-governance-gap.md`.

The most important C04 question is:

> Can V5 reliably keep consequential actions inside the exact authorized scope, and fail safely when it cannot?

## Relationship between C03 and C04

| Concern | C03 responsibility | C04 responsibility | What recent work established |
|---|---|---|---|
| Context selection | Select the smallest relevant context for the next decision/action | Ensure retrieved data, documents, and tool output do not become authority | Context metrics, retrieval guidance, stop rules, and outcome vocabulary were prototyped and partly ported |
| User intent and scope | Provide task/objective/scope as context | Determine what was authorized, constrain actions, and stop/reconfirm on material change | Workflow prompts and checkpoints cover several delivery transitions, not every default-work action |
| Knowledge | Select and use relevant records with provenance | Govern write, promotion, deletion, and whether knowledge can authorize action | C02 gates cover staging/promotion/correction; this is one governance surface, not general action safety |
| Tool/action boundary | May shape which sources/tools are selected | Define allowed, denied, approval-required, and stop behavior | exp4 had narrow shell/read controls; clean payload gate is strongest around AgenticLab knowledge, not an OS sandbox |
| Evaluation | Measure usefulness, misses, cost, and friction | Validate safety controls with prohibited and permitted cases | C03 metrics/cards are not a substitute for adversarial and benign governance tests |

**Finding:** C03 evidence can inform C04, but context-source policy cannot compensate for missing authorization semantics or enforcement.

## What C03 did establish

- Retrieval outcome vocabulary matters: applicable, no match, filtered, unavailable.
- A missing INDEX/MOC link is not proof of no-match.
- Prompt-generated metric labels need canonical semantics or a schema contract.
- Model/tool behavior is not perfectly reliable; paid-model traces used `readKnowledgeRecords` successfully while earlier free-model traces skipped or bypassed it.
- Workflow handoffs are clearer when the approved plan, validation details, and checkpoint are self-contained.
- Extra machinery is costly: selector tools, evaluation IDs/cards, PBI10 preflight, and broad guards were intentionally not made generic defaults.

## What C03 did not establish

- general action-authority semantics across default work and workflows;
- deterministic enforcement for consequential writes or shell actions;
- secret/protected-data safety beyond explicit textual boundaries;
- fail-safe behavior when an approval UI or guard is unavailable;
- that prompt instructions alone are reliable under long sessions or model variation;
- comprehensive governance from passing adapter unit tests.

## V4 governance as prior art

V4 mixed several different kinds of governance:

1. **Durable principles** — human approval, memory accuracy over completeness, epistemic honesty, intent before action, no silent scope expansion.
2. **Hard action prohibitions** — no hook bypass, no credential-file access, no unauthorized memory deletion, no removal of correction entries.
3. **Coordination rules** — blocker protocol, approval gates, bounded autonomy, loop caps.
4. **Memory-specific governance** — correction integrity, MOC triage, memory debt, DIGEST/semantic-map injection.
5. **Harness enforcement** — Pi damage-control extension, session guard, structural memory integrity checks.
6. **Context-efficiency discipline** — no speculative loads, bounded reads/searches, compute before reading, compact at boundaries.

V5 should preserve the valuable *functions*, not the V4 document structure, thresholds, paths, or adapter coupling.

## V5 current baseline

The current generic payload already covers a strong minimum:

- default work and explicit workflows share one scope/authority/safety contract;
- objective and project/task scope come from the user's current task;
- stored records, external content, tool output, confidence, and plans are not authority;
- a direct user request authorizes only the bounded action it names;
- answering a question or proposing a plan is not permission to edit;
- irreversible, destructive, security-sensitive, external-impact, and durable-knowledge actions need separate confirmation;
- material scope/risk changes require renewed scope checks;
- project knowledge starts as a candidate; staging leaves it inactive; promotion requires explicit UI confirmation;
- correction is append-only via supersession;
- retrieval distinguishes no-match, filtered, and unavailable;
- initialization previews all workspace-owned outputs and requires explicit approval before writing;
- `/plan`, `/implement`, and `/premortem` are opt-in and separately invoked;
- implementation logs are inside approved scope without a separate post-run approval;
- gate failure for durable knowledge writes fails closed;
- the Pi gate is explicitly not an OS sandbox.

This is governance in the knowledge and workflow domains. The remaining question is how those semantics behave across all consequential action paths.

## Primary gap to investigate

The first C04 review should focus on **action-scope fidelity and fail-safe behavior**, not on rule inventory.

Reasons:

- V4 and V5 both state strong authority semantics; the recurring failures are in execution fidelity.
- The Evershop source-listing event showed that an authorized bounded command was executed with broader path discovery than intended.
- C03 traces showed model-dependent tool invocation reliability.
- The C04 evaluation passed 3/4 tests; the out-of-scope staging test was inconclusive.
- The current Pi gate handles AgenticLab knowledge and pending/policy paths, but is explicitly not an OS sandbox.
- More semantic prose without fidelity evidence would add text, not assurance.

The review question:

> For each consequential action path, does V5 execute exactly the authorized scope, and if it cannot verify or enforce that scope, does it stop rather than claim protection?

## Required review work product

Produce a current-state traceability and risk review. This may be a new section in `C04.1` or a compact `C04.2` review appendix; do not create multiple overlapping documents.

For each governance concern, record:

1. **Semantic rule** — what must be true, in project-agnostic V5 terms?
2. **Action boundary** — which concrete action, data, file, command, or transition is governed?
3. **Current location** — operating contract, workspace instruction, delivery prompt, adapter, workspace policy, or nowhere.
4. **Enforcement class** — instruction-only, workflow gate, deterministic tool/adapter control, or external/host limitation.
5. **Evidence** — which test or real task demonstrates behavior? Include safe permitted cases, not only blocked cases.
6. **Failure behavior** — what happens when approval, gate, policy, workspace identity, or host capability is missing?
7. **Disposition** — already covered, narrow V5-native slice, defer with rationale, or unnecessary for this phase.

Review the currently enabled paths first:

- default work file reads/writes;
- shell/discovery commands;
- `/plan` checkpoint write;
- `/implement` approved edits and planned validation;
- knowledge candidate staging and promotion/rejection;
- initialization preview and writes;
- protected data and `.env` boundaries;
- commits, pushes, and external actions.

## Candidate first slice

If the review confirms a material gap, the first bounded slice should likely be:

> **Exact action-scope fidelity for consequential commands and writes.**

It must define:

- **Risk:** an action is broader, differently targeted, or differently parameterized than what the user authorized.
- **Allowed:** exact authorized path/command/write with stated exclusions.
- **Denied:** broader path, altered command, protected data/path, unrelated file, or scope expansion.
- **Ask/stop:** ambiguity, unavailable confirmation, unavailable guard, or unverifiable path mapping.
- **Host limitation:** lexical/tool interception is not an OS sandbox; shell wrappers, aliases, redirects, and nested processes may evade detection.
- **Tests:** benign exact case, benign near-miss, adversarial broader case, protected-path case, unavailable-approval case, and adapter-failure case.
- **Evidence location:** a real delivery task in an initialized workspace, not only synthetic unit tests.
- **Port rule:** do not move it into the clean payload until it has demonstrated value and low friction in real use.

Do not select this slice merely because it sounds prudent. Select it only if the review finds an actual gap in current behavior.

## Tradeoff rules for decisions

Use these rules during C04 design discussions:

1. **Prefer contract consolidation.** If a rule already exists in `AGENTS.md`, `operating-contract.md`, `knowledge-contract.md`, or delivery prompts, do not duplicate it in a new file.
2. **Prompt text first, deterministic enforcement second.** Add code only when the action is consequential, the rule is machine-checkable, and overblocking can be measured.
3. **No fixed thresholds without evidence.** Do not import V4's tool-call or fix-attempt numbers.
4. **No per-step gates for bounded authorized work.** Gate only scope changes, high-risk actions, and durable knowledge transitions.
5. **Fail closed where persistence is involved.** If approval or adapter confirmation is unavailable, do not persist through another path.
6. **Disclose enforcement gaps.** If the host cannot reliably intercept an action, say so; do not imply a sandbox.
7. **Measure overblocking.** A guard that blocks safe work is a defect, not success.
8. **Keep C02/C03 boundaries.** Knowledge lifecycle and context selection already have contracts; C04 should not absorb them.
9. **Keep the generic payload generic.** No exp4 paths, PBI IDs, evaluation cards, or project-specific policies may enter the clean payload.
10. **Prototype, then port.** A mechanism proven only in tests stays experimental until real delivery evidence supports broader use.

## Explicit non-goals

This phase does **not**:

- port V4 governance wholesale;
- reproduce V4 document structure for symmetry;
- import Tier A/B/C labels, fixed loop caps, `.env` regexes, Pi hooks, memory paths, or DIGEST injection;
- add a comprehensive governance engine;
- hard-code subjective judgments;
- claim C03/PBI10 tests prove system-wide safety;
- change the clean payload without a separate review and approval;
- authorize commits, pushes, destructive actions, or durable knowledge writes.

### Second fix round — write-capable shell reads (`f2040da`)

The `sed`/`find` hole found during review was closed in a separately approved follow-up.

The invariant for knowledge reads changed from "the command looks read-only" to "the shell cannot
write": only verbs that cannot create or modify a file are allowed (`ls`, `cat`, `head`, `tail`,
`wc`, `grep`, `file`, `stat`, `realpath`, `dirname`, `basename`, `less`, `more`, `read`) plus
navigation. `sed` and `awk` were removed because both can write (`sed w`, `sed -i`,
`awk print >`), and flag-by-flag modelling of their program text leaks. `find` remains allowed
without `-delete`, `-exec*`, `-ok*`, `-fprint*`, or `-fls`. Any output redirection disqualifies a
segment, so a redirect target is never silently exempted by an innocuous verb.

The action-scope gate gained `find` action classification and a latent-bug fix: `sed -i` had never
been classified as mutating, so in-place edits of out-of-scope files passed unchecked. `-i`,
`-i.bak`, `-ni`, and `--in-place` are now caught. Unknown verbs such as `npm test`, `pytest`, and
`uv run` deliberately keep their passthrough, because requiring extractable targets would block
ordinary approved validation runs.

Live evidence in a fresh Pi process: eight knowledge-gate probes matched intent (`sed -i`,
`awk … >`, `find -delete`, `find -fprint`, and `cat … > /tmp/...` blocked; prefixed `head`,
`grep -c`, and name-only `find` allowed) with no artifacts created and `INDEX.md` unchanged; four
action-scope probes with a synthetic single-file checkpoint matched intent (`sed -i README.md` and
`find backend … -fprint /tmp/...` blocked; `sed -n` and name-only `find` allowed).

### Third fix round — harmless removal segments and null redirects (`0d70107`)

Two frictions found by the real delivery task in exp8, both narrow:

- `rm <plan-checkpoint> && echo DELETED` was refused because the checkpoint-removal exception
  accepted only navigation segments. Any segment that cannot write (navigation, `echo`, `printf`,
  and read-only commands) is now harmless inside the exception; a write-capable segment still
  invalidates it.
- `ls <dir> 2>/dev/null` was classified as mutating, because any `>` counted as a write. Redirects
  whose target is `/dev/null` or a file descriptor (`2>&1`) are now ignored; `> file` and `2> file`
  still require scope.

A third change was tried and **reverted before porting**: releasing enforcement when the authorized
checkpoint removal is recognised. A live probe showed that deleting the checkpoint mid-run turned
the gate off, and two later out-of-scope writes succeeded. Enforcement therefore stays bound to the
checkpoint and fails closed when it cannot be verified. The implementation log is written before the
disposal step, so no legitimate action depends on that gap. General lesson: a gate must not be
releasable by the commands it guards.

Verified live: an approved `ls ... 2>/dev/null` was allowed and `sed -i` on an out-of-scope file was
blocked; the workflow correctly refused a mid-run checkpoint deletion. Ported as `0d70107`
(2 files) with the external suites at 15/15 plus 16/16 action-scope.

### Open gap — AgenticLab system knowledge captured as project knowledge

A record promoted in exp8 (`implementation-logs-gitignored`) describes the AgenticLab installation
itself — that `AgenticLab/`, `.pi/`, `knowledge-pending/`, and `implementation-logs/` are gitignored —
rather than anything about the host project. `AGENTS.md`, `plan.md`, and `implement.md` already say
that general AgenticLab payload policies and workflow behaviour must not be stored as target-project
knowledge, but the rule is semantic only.

Two contributing causes: the sanitized baseline's own `.gitignore` mixes application ignores with an
AgenticLab installation block, so a candidate derived from that file inherits system paths as
"project facts"; and candidate validation checks structure (scope, category, dedupe) but not subject
matter. The instance was partly test-induced because the probe text supplied that evidence, but
nothing in the adapter would have prevented it.

Proposed treatment, not yet approved: a deterministic subject guard on the candidate claim and title
(reject when they describe AgenticLab's own installation, paths, or workflow, with an actionable
message pointing at the canonical repository), plus one clarifying sentence tying it to `.gitignore`
entries. Treatment stays semantic for evidence text, which may legitimately quote project files.

An observed asymmetry is intentional and should not be "fixed": the knowledge gate restricts reads
and writes on knowledge paths, while the action-scope gate restricts only writes, because reading
workspace source is ordinary work.

### Disposition

Keep this as bounded hardening of the existing sinks. It is not evidence of broad governance
completeness, delivery benefit, or causal memory value.
