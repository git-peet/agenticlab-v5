# C03.2 — Context engineering prototype status and evidence-led next steps

**Status:** `candidate`; analysis derived from [C03-context-engineering.md](C03-context-engineering.md), [C03.1-context-engineering.md](C03.1-context-engineering.md), and the recent exp4 C03/C03.1 workflow-friction slice.

**Parent:** [C03-context-engineering.md](C03-context-engineering.md) · [`C03.1-context-engineering.md`](C03.1-context-engineering.md) · [`../README.md`](../README.md) · [`../../V5.2-roadmap.md`](../../V5.2-roadmap.md)

## Purpose

Record what the recent prototype establishes, what remains unverified or unimplemented from C03, and the evidence threshold for doing more work. This document is an analysis and decision aid, **not authorization or a recommendation to implement the full C03 model**.

## Current assessment

The recent exp4 work addressed friction in the thin context-engineering slice and added PBI10's deterministic plan preflight. It improved the `/plan` and `/implement` experience and has passing adapter tests. It does **not** establish that a comprehensive context-policy subsystem would improve delivery outcomes.

The prototype history warrants caution:

- C03 itself says it is not ready for a general context subsystem and treats the assembly model as a design proposal.
- Prior retrieval/context experiments were small and mixed: some relevant retrieval and navigation benefits were observed, but activation, replication, and time-benefit evidence was not consistent.
- The thin slice was followed by substantial friction repair. That is evidence to keep mechanisms lightweight and validate them in real delivery, not evidence that more policy machinery is needed.
- Recent exp4 tests establish specific code behavior (including guard/preflight checks); tests alone do not establish context quality or product-delivery benefit.
- The PBI10 preflight was implemented and unit-tested, but a live `/plan` run invoking it before final plan presentation has not been observed. This limitation is accepted for now; revisit if this layer causes a real blocker.

**Conclusion:** At present, there is **no demonstrated evidence that developing C03 further as a broad policy-enforcement or context-assembly subsystem would add value**. This is an absence of evidence, not proof that no narrow improvement could help. Do not treat the unimplemented items below as a roadmap commitment.

## What has been prototyped

### Existing C03 thin slice (as described in C03.1)

C03.1 records a thin slice for context-selection metrics and workflow-prompt guidance, including `recordContextSelectionMetric`, allowlisted source/event values, and context-selection instructions. It also records the metrics mechanism as ported to the generic clean payload. That historical status is not a claim that every later exp4 change has been ported.

### Recent exp4 workflow-friction and PBI10 slice

The exp4 work includes read-only directory listing during `/plan` while other shell commands are blocked, prompt refinements for context inspection and retrieval outcomes, C03 evaluation-marker/card handling, and PBI10's deterministic plan-preflight validator. The exp4 adapter suite passed 27/27 tests after implementation. A fresh PBI10 `/plan` run completed without ad-hoc correction; the preflight's invocation in a live `/plan` remains unverified.

These changes are exp4 prototype results. **No clean-payload changes are authorized or claimed by this document.** Porting any slice is a separate decision for the user after that slice is judged complete and sufficiently tested.

## Remaining C03 topics (not implementation commitments)

The C03/C03.1 candidates describe areas not covered by the recent slice. Their presence here is an inventory of possible questions, not a backlog to implement automatically.

| Topic | Candidate intent | Current status / evidence gap |
|---|---|---|
| Context-source inclusion policy | Decide when request, operating rules, current source, project knowledge, domain lens/procedure, workflow state, or task-local handoff is useful | Prompts provide guidance, but no general policy engine exists. No evidence currently justifies building one. |
| Workload families | Consider differing context needs for direct work, research, bug diagnosis, planning, implementation/resume, review, and bootstrap | Some explicit plan/implement flows have been exercised. There is no representative comparative evaluation across these families. |
| Technical project orientation | Provide a compact, source-cited starting model of a project's stack, boundaries, entry points, tests, and unknowns | C03 describes this as an initialization concern; its quality and recurring delivery benefit remain unproven. |
| Context usefulness and cost | Evaluate usefulness, missed/irrelevant context, cheaper derivation, handoff traceability, and interruptions | Some opt-in evaluation cards and content-free metrics exist. The sample is small and task-specific; it does not support broad claims. |
| Broader enforcement and integration | Ensure behavior across default work and explicit workflows | Default-work integration is deferred. Preflight's live invocation is not yet verified; reconsider only if a real run exposes a blocker. |

## Evidence-led next steps

1. **Do real project work using the current exp4 mechanisms.** Keep the work product-focused; AgenticLab changes should be driven by observed delivery problems rather than made the default purpose of PBIs.
2. **Capture qualitative observations and approved content-free metrics** where appropriate. Record concrete misses, irrelevant loads, unnecessary rediscovery, workflow interruptions, or useful context. Keep evaluation opt-in per task; do not add permanent telemetry by default.
3. **Look for repeated, consequential evidence.** A single awkward run or a theoretical gap is not sufficient reason to build a general mechanism. Distinguish model/harness behavior, prompt friction, retrieval limitations, and actual product-task needs.
4. **If a recurring problem appears, propose the smallest targeted experiment.** Define the specific problem, expected benefit, cost/friction, a real task on which to test it, and a stop/rollback condition. Prefer native tools and concise guidance unless evidence shows they are insufficient.
5. **Reassess C03 scope before implementation.** Consider policy enforcement, workload-specific guidance, and technical orientation individually; do not bundle them into a broad subsystem. A later clean-payload port requires separate user instructions and review.

## Deferred unless evidence changes

Do not proceed speculatively with:

- a general context-policy engine or source-gating framework;
- automatic workload classification and profiles;
- a context planner, fixed context budget, or broad orchestration layer;
- a bootstrap/orientation subsystem beyond a concrete demonstrated need;
- default-work integration, permanent telemetry, or clean-payload porting.

These may be reconsidered if real project delivery shows a repeated miss or cost that current source inspection, scoped retrieval, prompts, and native harness tools cannot address.

## Decision

For now, use the current prototype in real delivery and gather evidence. **C03 is not declared complete as a broad candidate, but neither is further implementation presumed valuable or approved.** The next decision is whether observed real-task evidence supports a narrowly scoped follow-up—not whether to implement every gap listed in C03.1.
