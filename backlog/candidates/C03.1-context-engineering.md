## What the full C03 candidate specifies (gap analysis)

The original candidate ([`C03-context-engineering.md`](C03-context-engineering.md)) defines a complete context-engineering model. The thin slice covers only the **metrics mechanism** and **prompt skeleton**. The following remain unimplemented:

### 1. Context Source Policy v0 — "when to include each source"

The candidate defines a table of 7 context sources with explicit inclusion rules. The thin slice only enables the **INDEX/MOC route** and **knowledge retrieval** without the full policy:

| Context source | When to include (candidate) | Current state |
|----------------|----------------------------|---------------|
| User request/objective/scope/authorization | Always | Implicit in prompt, not enforced |
| Operating/safety instructions | Baseline | In `AGENTS.md`/`PROJECT-SCOPE.md`, not policy-gated |
| Current source/tests/docs | When needed for present behavior | No scope/status filter before use |
| **Project knowledge via INDEX/MOCs** | **Only when task could benefit** | **Enabled but no "when to include" guard** |
| **Domain perspective/procedure** | **Optional, when materially improves focus** | **Not implemented** |
| **User-invoked workflow/approved plan/checkpoint** | **Only in that workflow context** | **Not enforced** |
| **Task-local candidate-learning handoff** | **Only after meaningful discoveries** | **Not implemented** |

### 2. Workload families — minimum context per work type

| Work family | Candidate minimum context | Thin slice |
|-------------|---------------------------|------------|
| Direct question/bounded change | Request/scope, relevant instructions, exact current source | No guard |
| **Research/exploration PBI** | **Research ACs, scoped source/docs, relevant records, optional domain perspective** | **Not implemented** |
| Bug diagnosis | Symptom/repro, relevant path/tests/contracts, task history only if it explains prior attempt | Not implemented |
| Explicit planning | User-invoked workflow prompt, PBI/ACs, code surface, relevant decisions/contracts | Partial (prompt exists) |
| **Approved implementation/resume** | **Approved plan, current phase/checkpoint, changed source/validation, carried candidates** | **Not enforced** |
| Test/review/premortem | Relevant diff/current source, ACs, integration contract, prior plan/capture handoff | Not implemented |
| Workspace bootstrap | Project identity/scope, harness setup, one-time technical orientation | Separate (initialize-workspace) |

### 3. Three-layer orientation concern (first-use vs. recurring)

| Layer | Candidate | Thin slice |
|-------|-----------|------------|
| Project identity/scope/data boundaries | `PROJECT-SCOPE.md` | Exists |
| AgenticLab/harness operation | Shared V5 contracts + project-local adapter/config | Exists |
| **Technical project orientation** | **Compact source-cited starting model of stack, module boundaries, entry points, test approach, known unknowns** | **Missing** |

The `initialize-workspace.md` prompt covers layers 1–2 but **does not build layer 3** (technical project orientation).

### 4. Evaluation questions (5 questions for real-task validation)

Not yet tested; should be run on representative tasks:

1. Did each loaded source materially help the next decision?
2. Was required context missed or irrelevant/off-scope context loaded?
3. Could the same result be derived more cheaply from current source?
4. Were knowledge candidates traceable and non-duplicative across phases?
5. How many user-visible interruptions were required?

### 5. Explicit exclusions (not selected)

No unconditional memory floor/Digest, embeddings/vector service, graph traversal, semantic reranker, autonomous multi-query loop, fixed context token budget, or permanent retrieval telemetry.

### 6. Preconditions and acceptance checks

Tests should cover: right-scope match, wrong-scope rejection, stale/superseded filtering, no match, filtered-only results, storage failure.

### 7. Next action from candidate

> C02's minimal INDEX → curated MOC → scoped-record interface is now an implemented prototype baseline in the clean payload. The local adapter performs scoped eligible-record search and returns explicit retrieval outcomes. The next V5 design pass is the context-assembly model for default and explicitly invoked workflow sessions: distinguish always-on operating rules, task/request context, current-source evidence, scoped project knowledge, optional domain perspectives/procedures, and approved plan/checkpoint state. Prefer staged, task-relevant loading and trace material sources; do not add an unconditional digest, general context planner, fixed token budget, or semantic retrieval.

## Next implementation directions

### Option A — Full C03 model
Add complete context source policy table, workload-family guards, evaluation framework, and three-layer orientation concern.

### Option B — Expand thin slice with policy enforcement (recommended next step)
Add the **scope/status filtering logic** that decides *when* each source layer is included — the core of the candidate's "when to include" table. Build on the existing metrics + prompt framework.

### Option C — Task-specific evaluations first
Run the 5 evaluation questions on representative tasks (direct question, research PBI, bug diagnosis, explicit planning, approved implementation/resume) to gather data on whether current context selection helps or hurts.

### Option D — Wait for real-task data
Use the system on actual PBIs, collect evaluation data, then decide what C03 features are actually needed.
